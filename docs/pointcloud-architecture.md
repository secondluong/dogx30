# 点云链路设计

从感知主机的 ROS 话题到遥控端屏幕上那几万个点，中间的每一步都是被
**带宽**和**依赖**这两件事逼出来的。这篇解释为什么这么做。

## 一、不装 ROS

板子上跑的是 Ubuntu 22.04（jammy），而 **ROS1 Noetic 官方只支持 20.04（focal）**。
在 jammy 上装 Noetic 只有三条路，没有一条干净：

| 办法 | 问题 |
| --- | --- |
| 源码编译整套 ROS | 上百个包，交叉编译一堆坑，升级系统就要重来 |
| conda / RoboStack | 引入第二套包管理，和系统 Python 打架 |
| Docker 跑 focal | 多一层容器与网络配置，ROS 的多播发现在容器里很折腾 |

而我们从 ROS 那边只想要一件事：**订阅两三个话题**。为此背上整个 ROS 运行时，
性价比极低。

所以直接说 ROS 的线上协议。这条链路上只有两个协议：

- **XML-RPC**（HTTP + XML）：向 master 注册订阅、问发布者要连接地址
- **TCPROS**：一次连接头握手，之后就是「4 字节小端长度 + 消息体」的裸流

两个都很简单。代价是消息类型的 `md5sum` 要手工对齐（填错会被发布者直接拒连），
收益是**零依赖**——板子上除了我们自己的二进制什么都不用装。

这和项目里自己写 WebSocket、自己写 UDP 协议是同一个取舍。

实现在 `rk3588/src/xmlrpc.cpp` 与 `rk3588/src/ros_client.cpp`。
只做订阅，不做发布和服务：我们对机器人本体是**只读**的，
运动指令一律走已有的 UDP 通道，不从 ROS 侧下发。

### 从节点服务端

订阅者要给 master 一个回调地址，master 在发布者变化时会调 `publisherUpdate`。
本来可以不实现——注册照样成功——但那样 master 日志会一直刷错误。
**机器狗是生产设备，不该被我们污染**，所以还是实现了一个最小的 XML-RPC 服务端。

## 二、带宽：从 100 Mbps 砍到 1.5 Mbps

四台 Mid-360 合起来每秒约 80 万点。原始 XYZI 是 16 字节/点，
也就是 **100 Mbps 量级**。而 MESH 实测只有十几 Mbps，还要分给视频。

砍了四层：

| 手段 | 效果 | 说明 |
| --- | --- | --- |
| 抽帧 10 Hz → 2 Hz | ÷5 | 遥控看障碍不需要 10 Hz |
| 距离裁剪 0.4–30 m | 约 ÷1.5 | 近处是狗自己，远处稀疏且无用 |
| 体素降采样 10 cm | 约 ÷5 | 同格子只留一个点 |
| 坐标量化 float32 → uint16 | ÷2 | 见下 |

实测结果：**单帧 88 KB，2 Hz 约 1.44 Mbps**，落在 2–3 Mbps 的预算内。

### 量化是白拿的

以包围盒最小角为原点，把跨度均分到 uint16 上。以 ±40 m 的场景算，
分辨率约 1.2 mm——**远小于雷达本身的精度**，也就是说这一半带宽省得没有代价。

用 65000 而不是 65535 做上界，是给浮点舍入留余量：溢出会绕回成 0，
表现为远处的点突然跳到原点，这种问题极难查。

遥控端更省事：uint16 直接喂给 WebGL，用 `vertexAttribPointer` 的
`normalized=true` 让 GPU 还原，CPU 侧连一次遍历都不用做。

### 自适应体素

楼道和空旷场地的点密度差很多，固定体素边长在一边合适、在另一边就不合适。
所以点数超限时自动放大体素，偏少时慢慢收回来，让点数自己收敛到上限附近。

单帧超限时还会先等距抽稀一次——**这一帧必须先把带宽压住**，
不能指望调大体素立刻生效，那要重算整帧。

## 三、按需启停

没有任何客户端订阅时，网关**根本不去连感知主机**。

理由不是省板子的 CPU，而是：机器狗是生产设备，不该因为我们挂了个订阅者
就一直多一路 30 MB/s 的 TCP 流。遥控端切后台时也会自动退订。

启停由一个独立的管理线程执行，不在 WebSocket 消息回调里做——
`RosClient::Stop()` 要 join 订阅线程，卡在消息回调里会连带拖住控制指令。

## 四、两个差点埋进去的坑

都在关停路径上，本地不测就会在现场变成「`systemctl restart` 卡死」。

**一、阻塞的 `accept()` 叫不醒。** Linux 上关掉监听套接字**并不保证**唤醒
阻塞在 `accept()` 里的线程，`join()` 会永远等下去。必须先 `select` 再 `accept`。
（已有的 `WsServer` 本来就是这么写的，新加的 XML-RPC 服务端一开始漏了。）

**二、`connect()` 不受 `SO_SNDTIMEO` 约束。** 感知主机掉电时，内核会重传 SYN
一分多钟。而这条路径就在网关的启停流程上——结果是关一次网关要等两分钟。
必须用非阻塞 connect 加 `select` 自己控超时，见 `net_util.cpp`。

`tools/shutdown_test.sh` 专门用一个**不可达**地址（RFC 5737 的 `192.0.2.1`）
测这两条路径。修好后关停耗时 284 ms。

还有第三个，在下行方向：`WsServer` 的发送在阻塞 `send()` 时持有连接的发送锁。
一帧 88 KB 的点云在拥塞的 MESH 上会阻塞很久，而 10 Hz 的遥测广播要拿同一把锁——
**一个看点云的客户端能把所有人的遥测卡住**。加了 2 秒发送超时，超时即丢帧：
迟到的点云没有价值，堆积只会让延迟越滚越大。

## 五、没有实机怎么测

`tools/ros_sim.py` 是一个假的 ROS master 加发布者，实现的是**真 ROS 的线上协议**，
不是我们自己约定的简化版。所以在它上面能跑通，到现场大概率也能跑通。

它造的场景是有结构的——地面、两侧墙、两个箱子、一堵绕原点转的墙——
而不是随机点。纯随机点云看不出坐标系有没有搞错，也看不出量化有没有失真；
有结构的场景在渲染端一眼就能发现问题。那堵转动的墙用来确认帧真的在更新。

`tools/cloud_probe.py` 把二进制帧解回坐标做断言，覆盖帧格式、点数上限、
反量化精度、抽帧是否生效、**退订后是否真的停发**。最后一条最容易写错也最容易
被忽略：不生效的话点云会一直占着带宽，现场只会看到视频变卡，很难联想到点云。

## 六、还没做的

**现在下发的是机体系当前帧，不是累积地图。** 也就是说遥控端看到的是
「此刻雷达打到了什么」，狗一动，画面整体跟着动。

这对避障和判断前方地形已经够用，但要看「走过的地方长什么样」就不行，
那需要 LIO 做配准。`docs/reference-mysystem.md` 里记的那条经验在这里同样成立：
**必须转发世界系已配准点云**，把原始帧丢给前端自己拼是行不通的。

好消息是这一步不影响协议：等 LIO 上了，网关换个订阅话题就行，
二进制格式和遥控端渲染都不用动。

其余待办：

- FAST-LIO2 / Point-LIO 建图定位，四雷达合并云的降采样调参
- 逐点时间戳。`/lidar_points` 里有没有还没确认，没有就做不了扫描内运动畸变补偿，
  在四足这种剧烈晃动的载体上精度会明显变差，那时得改订 `/livox/lidar` 的 `CustomMsg`
- 狗自身位姿叠加显示（`/leg_odom`）
- **感知主机 ROS 的可达性至今没有现场验证过**，见 `hardware-integration.md`
