# RK3588 首次部署（NanoPC-T6-Plus）

从一块空板子到能用平板遥控机器狗的完整步骤。

**总原则：所有软件工作都在桌面上完成并用仿真器验证过，再上机器狗。**
狗身上没有显示器、没有互联网，趴在地上调板子既慢又危险。
按本文走，上狗那一步只剩接线和改一个 IP。

分三个阶段：

| 阶段 | 在哪做 | 产出 |
| --- | --- | --- |
| 一、桌面准备 | 办公桌，接显示器和能上网的网线 | 板子装好系统、网关跑通仿真器 |
| 二、上狗接入 | 机器狗旁 | 遥控实机走起来 |
| 三、遥控链路 | 现场 | 手柄经 MESH 连上控制台 |

---

## 快速通道：一键安装包

不想逐步走的话，用自解压安装包。**在开发机上**生成：

```bash
bash deploy/make_installer.sh
# → dist/x30-installer-<日期>.run，约 230 KB
```

拷到板子上（U 盘请用 **FAT32**，很多板子镜像不带 exFAT 驱动），然后：

```bash
chmod +x x30-installer-*.run
sudo ./x30-installer-*.run
```

在桌面上**双击它也行** —— 壳会自己找一个终端模拟器把自己重新跑起来，
免得双击之后"看着什么都没发生"。

它把下面这些串成一条：环境检查 → 系统调优 → 编译 → 问参数 → 装服务 → 体检，
每一步做过的会自动跳过，可以反复跑。源码会留一份在 `~/dogx30`（`checkup.sh`、
`rtsp_probe.py` 这些排查工具都在里面，装完就删掉的话出问题时手边反而没工具）。
装完还会在桌面上放三个快捷方式：控制台、体检、日志。

```bash
sudo ./x30-installer-*.run --yes            # 全用默认值，不提问
./x30-installer-*.run --extract ~/dogx30    # 只解压不安装，之后手工分步
```

**它不会替你做判断。** 参数都会问一遍并给出默认值，最后跑一遍体检把结果摊开。
装机当天真正的难点从来不是敲命令，而是下面这些「为什么」——
所以第一次装还是建议照着后面的分阶段步骤走一遍，
之后重装、升级、换板子再用一键包。

## 目标硬件：FriendlyELEC NanoPC-T6-Plus

关键参数（取自官方 wiki）：

| 项 | 参数 | 对本项目意味着什么 |
| --- | --- | --- |
| 尺寸 | 110 × 82.5 mm | 装机器狗背上很宽松 |
| 板载存储 | 32/64/256GB eMMC | 不用 TF 卡，振动工况下更可靠 |
| 供电 | 12V 直流，**5.5×2.1 圆口 + 2Pin 3.5mm 端子** | 端子口很适合装机，见下 |
| 供电容差 | 5–20V，官方推荐 12V | 对 DC-DC 的输出精度要求不高 |
| 网口 | 2 × 2.5GbE（RTL8125BG） | eth0 接机身，eth1 接交换机，**两口不够用** |
| 无线 | M.2 E-Key 2230 插槽（**本机已装模块**） | 备用调试通道，遥控走 MESH 不走它 |
| 4G | M.2 B-Key（**本机已装模块**） | 运维/云端通道，**不用于遥控**，见第 18 节 |
| 扩展 | M.2 M-Key（NVMe） | |
| 按键 | Power、Reset、MASK | Power 键的存在是个坑，见下 |
| 工作温度 | **0℃ ~ 70℃** | 低温端只到 0℃，冬季室外要注意 |

### 四点提醒

**必须确认上电自启。** 官方文档明确写着"部分型号需要按 Power 键才能启动"。
装到机器狗背上以后没人能去按它，所以**桌面阶段就要验一次**：拔掉 12V，
再插上，看它是不是自己起来。

如果非按不可，要么在 U-Boot/设备树里找上电自启配置，要么把 Power 键排针常闭短接。
这件事不确认，第一次装好上狗会直接卡在"板子不亮"，而那时外壳已经拧上了。

顺带说，运动主机启动比板子慢是正常的，网关的心跳是无状态的，
它会一直重试到运动主机起来，不需要做启动顺序编排。

**供电优先用 2Pin 3.5mm 端子，不要用圆口。** 这块板子两种口都有。
5.5×2.1 的圆口 DC 插头在持续振动下有松脱风险，机器狗走起来一颠就可能瞬断；
3.5mm 螺丝端子拧紧了就不会松，DC-DC 模块的输出直接压线接上去正好。

**无线要另外买。** T6-Plus 没有板载 WiFi，只有 M.2 E-Key 插槽。
平板要连板子，这一环绕不开，见阶段三。

**工作温度只到 0℃。** 这是消费级 SBC 的常见规格，比工控板窄。
如果冬季要在室外用，得考虑保温或者换工业级方案。

## 阶段一：桌面准备

板子接显示器（HDMI）、键盘、和一根**能上网的**网线。
这个阶段结束时，板子上所有软件都装好且验证过。

### 1. 选烧录方式

官方网盘 `01_系统固件` 下有三个目录，区别是**系统最终跑在哪**，
不只是烧录手段的差别：

| 目录 | 文件名含 | 系统跑在 | 用不用 |
| --- | --- | --- | --- |
| `01_SD卡固件` | `-sd-` | SD 卡 | ✗ 振动 + 硬断电会把卡搞坏 |
| `02_SD卡刷机固件(SD-to-eMMC)` | `-eflasher-` | eMMC | **✓ 用这个** |
| `03_USB线刷固件(USB-to-eMMC)` | `-usb-` | eMMC | 下载存着，当恢复手段 |

选 **02（eflasher）** 的理由：只需要一张 microSD 加 Win32DiskImager，
主机上什么驱动都不用装；卡做好之后重刷只要插卡、上电、等、拔卡，
开发期你大概率要反复重刷，这个差别很实在。

**03 建议一并下载存着。** 万一 eMMC 里的 bootloader 刷坏、eflasher 也进不去，
就靠它救：断电 → 按住 MASK 键 → 上电 → 状态灯亮 4 秒后松手 →
RKDevTool 会显示 "Found One MASKROM Device"。

### 2. 选系统镜像

选 **`rk3588-eflasher-ubuntu-jammy-*-desktop-arm64-<最新日期>.img.gz`，内核 6.1.y**。

装完第一件事就是关掉桌面：

```bash
sudo systemctl set-default multi-user.target
sudo reboot
```

选带桌面的镜像看着反直觉——我们要的是无头服务器。两个理由：

- **它预装并验证过 rkmpp**。官方说明写明"集成 rkmpp/mpv 实现视频硬件加速"，
  rkmpp 正是第三阶段做 H.264 硬编推流要用的库。从一个 MPP 已知可用的镜像出发，
  能省掉后面自己折腾编码器的大量时间。
- **另一个候选的基础系统太旧**。`friendlycore-focal` 虽然是纯命令行、看着更干净，
  但它基于 Ubuntu 20.04，自带 CMake 3.16.3——正好卡在本项目 `CMakeLists.txt`
  要求的最低线上，一点余量没有，GCC 也只有 9。jammy 是 22.04，CMake 3.22、
  GCC 11，宽裕得多，LTS 也支持到 2027。

桌面一条命令就关了，eMMC 和内存都不缺这点空间，不值得为省它换一个更旧的底子。

明确**不要**选：FriendlyWrt（OpenWrt，做路由器的，工具不对）、Android/Android TV、
Armbian（第三方，对 MPP 的支持没保证，会卡死视频阶段）。

想两个都试的话有个 `rk3588-eflasher-multiple-os-YYYYMMDD-25g.img.gz`，
一张卡装多个系统手动挑，要 32GB 以上的卡，注意它**不会**开机自动刷。

**务必下最新固件。** 网盘里可能还挂着 2022 年的旧快照，RK3588 的 BSP 这两年
改进很大，用旧的会平白踩一堆已修复的坑。

### 3. 烧录

1. 准备一张 8GB 以上的 microSD。
2. 下载 `02_` 目录下的 eflasher 固件，解压 `.gz` 得到 `.img`。
3. Windows 下**以管理员身份**运行 Win32DiskImager（在网盘 `05_工具软件` 里），
   选好盘符和镜像，点 Write。
4. 卡插进 T6-Plus，上电。EFlasher 会**自动开始**把系统写进 eMMC，
   进度可以看 HDMI 输出或板上状态灯。
5. 完成后拔卡，板子自动重启，从 eMMC 启动新系统。

注意第 4 步是自动开刷的，**eMMC 里的原有数据会被覆盖**，有东西先备份。

### 4. 首次开机

```bash
passwd                                        # 改掉默认口令
sudo hostnamectl set-hostname x30-payload
sudo timedatectl set-timezone Asia/Shanghai
```

### 5. 换源并更新

arm64 的 Ubuntu 用的是 `ports.ubuntu.com` 而不是 `archive.ubuntu.com`，
照抄 x86 的换源命令不会生效：

```bash
sudo sed -i 's|http://ports.ubuntu.com|https://mirrors.tuna.tsinghua.edu.cn|g' \
    /etc/apt/sources.list
sudo apt update && sudo apt upgrade -y
```

部分固件把源写在 `/etc/apt/sources.list.d/` 下，上面没效果就去那个目录看。

### 6. 装工具链

网关是零第三方依赖的，只要编译器：

```bash
sudo apt install -y build-essential cmake git python3
cmake --version && g++ --version     # 需要 CMake ≥ 3.16、支持 C++17 的 GCC
```

### 7. 把源码送上板子

工程目前还没有 git 远端，而且板子首次上电时网络多半也没配好，所以走离线包。
**在开发机上**（Windows 用 WSL，或任意 Linux/macOS）打包：

```bash
bash deploy/package.sh
# → dist/dogx30-<日期>.tar.gz，约 100 KB
```

包里只有源码和脚本，不含编译产物——二进制一律在板子上现编，整个工程只依赖
编译器，十几秒就好，省得纠结交叉编译的 ABI 兼容。脚本还会顺手把 `.sh`/`.py`
的换行统一成 LF，避免 Windows 的 CRLF 到了板子上报 `command not found`。

送过去有两条路，任选：

```bash
# A. 网络可达时，从开发机推
scp dist/dogx30-*.tar.gz pi@<板子IP>:~/

# B. 板子还没网，U 盘拷贝后在板子上
sudo mount /dev/sda1 /mnt && cp /mnt/dogx30-*.tar.gz ~/
```

然后在板子上解压、固化系统：

```bash
cd ~ && tar xzf dogx30-*.tar.gz && cd dogx30-*
sudo bash deploy/bootstrap.sh
sudo reboot
```

> 后续要迭代升级的话，建议尽早把工程推到内网 Git 服务器，之后 `git pull` +
> 重跑 `install.sh` 就能升级，比反复打包舒服。离线包这条路始终可用，作为兜底。

脚本里每一项都写了为什么，概括是四类：CPU 调度器锁 performance（默认 ondemand
降频后唤醒要几十毫秒，50 Hz 控制回路的抖动直接表现为机身晃动）、禁休眠与自动升级、
关 WiFi 省电（省电模式的几百毫秒延迟尖峰对遥控是致命的）、加大网络缓冲。

### 8. 验证上电自启

**这一步别跳过**（原因见前面的提醒）：拔掉 12V，等几秒，再插上，
看板子是不是自己起来、系统自己进到登录提示符。

### 9. 用仿真器自测

现在还没接机器狗，先在板子上自己跟自己跑通全链路：

```bash
cd ~/dogx30
cmake -S rk3588 -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
bash tools/serve_test.sh            # 应当 20 项全 PASS
```

然后手动开一遍控制台，确认界面能用：

```bash
python3 tools/x30_sim.py &
./build/x30_gateway --robot-ip 127.0.0.1 --serve --web web
```

拿另一台电脑浏览器打开 `http://<板子IP>:8080/`，点「申请控制权」→「坐 / 站」
→「力控站立」→「起步 / 停步」，推左摇杆，看遥测盘的速度和里程计跟不跟着动。

**能在这里操作出反应，说明整套软件是好的。** 之后上狗出的任何问题，
都只可能在网络配置和机器狗那侧，排查范围一下子小很多。

## 阶段二：上狗接入

### 10. 配静态 IP

板子只有两个网口，而载荷侧有 MESH 电台、双光布控球、气体监测三个网络设备，
**必须在 eth1 后面挂一个小交换机**（5 口千兆工业级、12V 供电，跟板子共用同一路
DC-DC 即可）：

```
eth0 ── 机器狗机身                      192.168.1.0/24
eth1 ── 工业交换机 ─┬─ MESH 电台        192.168.10.0/24
                    ├─ 双光布控球
                    └─ 气体监测
```

| 板子网口 | 接到 | 地址 | 用途 |
| --- | --- | --- | --- |
| eth0 | 机身 Ethernet Port 1 | `192.168.1.120/24` | 运动主机 `.103`、感知主机 `.105` |
| eth1 | 工业交换机 | `192.168.10.2/24` | 遥控链路 + 载荷设备 |

**两个网段务必分开。** eth0 上跑的是 50 Hz 轴指令，是安全相关的实时链路，
不该和视频码流混在一起争带宽。载荷统一放 `192.168.10.0/24`，物理上就隔离了。

板子是 2.5G、机身多半是千兆，会自动协商到 1000M，没问题；
交换机是千兆也够——载荷侧总共也就几 Mbps。

先确认网口名和物理口的对应关系——插一根网线看哪个变 UP：

```bash
ip -br link
```

**配静态地址之前，先用 DHCP 探一下尾部调试网口到底通到哪。** 厂家拓扑图显示
这个口和交换机之间隔着一个路由器，如果它在做 NAT，板子就不在
`192.168.1.0/24` 里，后面的遥测永远回不来（详见
[system-architecture.md](system-architecture.md)）：

```bash
ip -br addr show eth0     # 看拿到的是哪个网段
ping -c3 192.168.1.103
```

拿到 `192.168.1.x` 且 ping 得通，说明是桥接，继续往下配静态地址：

```bash
sudo bash deploy/bootstrap.sh --static-ip 192.168.1.120/24 --iface eth0
```

**拿到别的网段就先停下来。** 那说明中间的路由器在做 NAT，得换个接入点
（交换机空口直连，或把路由器改成桥接）。此时硬配 `.120` 只会让网卡
配置和真实拓扑对不上，症状是"指令发得出去、遥测收不回来"，
和 `network.toml` 没登记的表现完全一样，很难分辨。

**eth1 本阶段先不配静态地址**，保持 DHCP 当维护口用：要上网装包或从笔记本
ssh 进来，插根线就行，完全不用动 eth0。等交换机和 MESH 到位了再按第 16 节配
成 `192.168.10.2/24`。

**eth0 不要配默认网关。** 机器狗内网没有互联网出口，配了会抢走默认路由，
之后想通过别的口上网就不通了，症状是"能 ping 通 IP 但域名解析不了"，
很容易查错方向。`bootstrap.sh` 里已经显式设了 `never-default`。

验证：

```bash
ping -c3 192.168.1.103     # 运动主机：所有行走控制
ping -c3 192.168.1.105     # 感知主机：地形图（上下楼）、点云、机身相机
ping -c3 192.168.1.106     # 导航主机：选装件，多半不存在，不通属正常
```

机身出厂就是这三个地址，不用配。它们的分工：

| 地址 | 主机 | 上面有什么 | 不通的后果 |
| --- | --- | --- | --- |
| `.103` | 运动主机 | UDP 控制口 43893、遥测回发 | 什么都动不了 |
| `.105` | 感知主机 | 地形图模块、ROS master、`rtsp://…:8554/test` | 上不了楼、没点云、没机身相机 |
| `.106` | 智能控制器 | 官方 `jy_cog` 建图定位 | 见下 |

**前两个不通就先别往下走**，检查网线插的是不是尾部调试网口、
机器狗有没有完全启动。

`.106` **通不通都请反馈一声**。早期资料说本机不含智能控制器，但厂家给的
拓扑图上画着它，两种说法对不上。它若真在，官方建图定位套件可用，
SLAM 不用在板子上从头做，后续工作量差别很大。第 13 节的体检脚本带了这一项。

雷达不在这个网段。四个 Livox 挂在**独立的雷达交换机**上，走 `192.168.2.0/24`，
从尾部网口够不到 —— 所以点云只能经感知主机的 ROS 话题拿。
这也是载荷网段选 `192.168.10.0/24` 而不是 `192.168.2.x` 的原因。

### 11. 在运动主机上登记本机

**这一步不做收不到任何遥测**，而且指令还发得出去，极易误判成"通了"。
详见 [hardware-integration.md 第四节](hardware-integration.md)。

要点是把 `192.168.1.120` 和端口 `43897` 按**相同索引**追加到 `network.toml`
的 `ips` 与 `ports` 两个数组，然后重启运动程序。

### 12. 供电

72V→12V DC-DC 的选型见 [hardware-integration.md 第一节](hardware-integration.md)。
输出接板子的 **2Pin 3.5mm 端子**，不要用圆口。

**第一次联调先用外部 12V 适配器**（官方推荐 12V/2A 起，满配建议 12V/4A），
板子和狗各自独立供电，出问题能单独断电。控制链路验证完再接机身供电。

### 13. 安装为系统服务

```bash
cd ~/dogx30-*
sudo bash deploy/install.sh \
    --robot-ip 192.168.1.103 \
    --perception-ip 192.168.1.105 \
    --port 8080
systemctl status x30-gateway
```

`--perception-ip` 指向感知主机上的地形图模块，**上下楼步态必需**：运动主机只
认步态指令，地形图模式没设对的话它会静默忽略，表面上看就是"点了没反应"。
两个默认值就是官方文档给的地址，一般不用改。

这里先不加 `--bind`，本阶段还没接遥控链路，监听全部网卡便于从笔记本调试。
等第 18 节确定了遥控链路走哪个网卡，再把监听范围收紧。

这些参数写进 `/opt/x30/conf/gateway.conf`，systemd 单元只指向它。装完之后
**在控制台的「设置」里就能改**，不用再重装，也不用编辑 systemd 单元。设置密码是
`54longqr`。

装完立刻跑一遍体检：

```bash
bash deploy/checkup.sh
```

它把服务状态、端口监听、暴露面、机器狗可达性、**遥测是否真的收得到**、
ROS、相机、温度、磁盘一次查完，每一项要么过、要么直接说下一步做什么。
只读、不改配置、可以反复跑，所以后面每改一次东西都可以再跑一遍。

这个阶段有几项必然是红的（还没接遥控链路和相机），正常。现在只需要
「服务」和「机器狗」两节全绿。想只看当前生效的参数就加 `--config-only`。

其中**「遥测」那一节最值得盯**。它单拎出来是因为 ping 通不等于收得到数据：
运动主机只往 `network.toml` 里登记过的地址回发，没登记的症状是
"指令发得出去、数据收不回来"，而这两件事在界面上长得很像。

### 14. 实机验证

**第一次务必把机器狗架起来或在空旷处操作，留一个人守着遥控器上的软急停，
人与机器人保持 2 米以上。**

先用命令行验证，比开浏览器直接：

```bash
sudo systemctl stop x30-gateway      # 避免两个进程抢端口
cd ~/dogx30
./build/x30_gateway --robot-ip 192.168.1.103 --local-port 43897 --interactive
```

敲 `s` 看遥测，显示"未收到数据"就回第 11 步查 `network.toml`。

确认遥测正常后按 [hardware-integration.md 第六节](hardware-integration.md)
的顺序走一遍。其中 `freeze` 那步是安全层验证，**不要跳过**——
必须亲眼看到速度自己归零，才说明看门狗真的生效了。

验完把服务起回来：`sudo systemctl start x30-gateway`

## 阶段三：遥控链路接入

遥控走 **MESH 自组网**，不走 WiFi。板子上的三个通道分工不同，不要混用：

| 接口 | 干什么 | 为什么 |
| --- | --- | --- |
| eth1 → MESH | **遥控链路**，手柄从 MESH 另一端接入 | 自组网直连，延迟低，覆盖比 WiFi 远 |
| 4G（wwan0） | **运维/云端通道**，远程 ssh、对时、日后传云 | 延迟抖动大且在运营商 NAT 后 |
| WiFi（wlan0） | **备用调试**，临时用笔记本连 | 平时可以不开 |

### 15. 配 eth1 与载荷网段

交换机接好后，给 eth1 配静态地址：

```bash
sudo bash deploy/bootstrap.sh --static-ip 192.168.10.2/24 --iface eth1
```

MESH 电台、布控球、气体监测按各自说明书配到同一网段（如 `.11 / .12 / .13`），
逐个 ping 通再往下走：

```bash
for ip in 192.168.10.11 192.168.10.12 192.168.10.13; do
  ping -c2 -W1 "$ip" >/dev/null && echo "$ip 通" || echo "$ip 不通"
done
```

**MESH 两端要在同一网段但不同地址**，手柄侧拿到 `192.168.10.x` 之后，
直接访问 `http://192.168.10.2:8080/` 就能开控制台。

### 16. 确认 4G 与 WiFi 模块被识别

```bash
ip -br link      # 应有 wwan0（或 usb0）
lsusb            # 4G 模块多以 USB 设备出现
```

确认天线接好了。模块本身不带天线，靠 IPEX/u.FL 转接线接外置天线；
**如果用官方 CNC 金属外壳，天线必须引到壳外**，金属壳会把信号屏蔽掉。
这一条最容易被忽略，症状是"能连上但一走远就断"。

### 17. 处理默认路由冲突

现在板子上有多个网络接口，**只能有一个默认路由，且必须是 4G**：

| 接口 | 默认路由 | 说明 |
| --- | --- | --- |
| eth0（机器狗） | **不要** | 内网无互联网出口，抢了默认路由会导致域名解析不了 |
| eth1（载荷/MESH） | **不要** | 载荷网段同样没有互联网出口 |
| wwan0（4G） | **是** | 唯一的互联网出口 |

`bootstrap.sh` 里已经给 eth0 设了 `never-default`。配完检查一遍：

```bash
ip route            # default 那一行应当只有一条，且走 wwan0
ping -c3 www.aliyun.com
```

出现多条 default、或者 default 走了 eth0，就是这里配错了。

顺带一个好处：有了 4G，板子能对时了。T6-Plus 有 RTC 但不一定装了纽扣电池，
没有网络时每次断电重启系统时间都会回退，日志时间戳会乱。确认一下：

```bash
timedatectl        # System clock synchronized 应为 yes
```

### 18. 把遥控端口挡在 4G 之外

**这一步关系到安全，不要跳过。**

遥控协议目前**没有身份认证**——任何能连上 8080 端口的人都可以申请控制权
然后驱动机器狗。之前没有广域接口时这只是个内网服务，装了 4G 就不一样了。

网关默认监听 `0.0.0.0`（全部网卡），启动时会打印警告。用 `--bind`
把它限定到遥控链路的地址：

```bash
# 你们的拓扑：遥控走 eth1 → 交换机 → MESH 电台，绑到 eth1 的地址
sudo bash deploy/install.sh --robot-ip 192.168.1.103 --bind 192.168.10.2

# 若临时改走机器狗自带 WiFi，绑到 eth0 的地址
sudo bash deploy/install.sh --robot-ip 192.168.1.103 --bind 192.168.1.120
```

绑到 `192.168.10.2`（eth1）之后，4G 那侧就完全够不着 8080 了——这正是目的。

控制台的「设置」里也能改这一项，但**改之前先想清楚从哪个地址访问控制台**：
新地址一旦不覆盖你现在用的这条路，重启后页面就连不回来了，只能上命令行。
网关会拒绝一个不属于本机任何网卡的地址（那会让服务直接起不来），
但它没法知道你是从哪儿连过来的。

绑定不存在的地址不会导致启动失败（代码里开了 `IP_FREEBIND`），
所以不用担心开机时网关比网络配置先就绪。

改配置本身要密码（`54longqr`）。这道门就是为
这一步存在的：否则任何能连上 8080 的人都可以把监听地址改回 `0.0.0.0`，
上面所有的收紧动作就白做了。

再加一道防火墙，避免以后有人手滑改回 `0.0.0.0`：

```bash
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw allow in on eth1 to any port 8080 proto tcp
sudo ufw enable
```

装好后从板子上自己验一次，确认只有该通的地址通：

```bash
bash tools/bind_check.sh
```

**远程运维建议只留 ssh，并且用密钥登录、禁用口令。**
真要从外网看控制台，走 WireGuard 之类的隧道，不要把 8080 直接暴露到公网。

顺带说明为什么 **4G 不能用来遥控**：一是运营商 NAT 后手柄根本直连不到板子，
要做穿透就得架中转服务器；二是 4G 的延迟抖动经常到上百毫秒，
而遥控端要以 2 Hz 发心跳、网关 3 秒租约到期就撤销控制权，
链路一抖机器狗就会自己停下。4G 适合做远程查看和运维，不适合实时操控。

### 19. 装媒体服务（视频与对讲）

视频走 MediaMTX：从相机拉 RTSP，转封装成 WebRTC 发给遥控端，**中间不转码**。
选型与依据见 [media-architecture.md](media-architecture.md)。

下载 **linux-arm64** 的单文件二进制放到 `bin/`，重跑 `install.sh` 就会自动
带上媒体服务：

```bash
# 在能上网的机器上下载，或板子通了 4G 直接下
# https://github.com/bluenviron/mediamtx/releases
tar xzf mediamtx_*_linux_arm64.tar.gz
sudo install -m 755 mediamtx /opt/x30/bin/mediamtx
sudo bash deploy/install.sh --robot-ip 192.168.1.103 --bind 192.168.10.2
```

然后改两个配置文件，**两处的 path 必须一一对应**，改一处就要改另一处：

| 文件 | 改什么 |
| --- | --- |
| `/opt/x30/mediamtx.yml` | 相机的 RTSP 地址与密码；监听地址改成本机 eth1 |
| `/opt/x30/media.json` | `webrtc_base` 改成**遥控端能访问到的地址** |

`webrtc_base` 千万别填 `127.0.0.1`——这个串会原样下发给遥控端浏览器去拉流。

在球机自己的界面上把码流配成下面这样，配好之后 RK3588 只做转封装，
CPU 几乎不占：

| 码流 | 分辨率 | 帧率 | 码率 | 编码 |
| --- | --- | --- | --- | --- |
| 主码流 | 1920×1080 | 25 | 3 Mbps **CBR** | H.265 |
| 子码流 | 640×480 | 10 | 400 kbps **CBR** | H.264 |

**一定要用 CBR 不要用 VBR。** 狗在走、云台在转时画面剧烈变化，VBR 的码率会
飙上去把 MESH 占满，然后控制报文排队、租约超时、狗自己停下，现场看起来就是
「莫名其妙断控」。宁可画质恒定差一点。

验证：

```bash
systemctl status x30-media
journalctl -u x30-media -f
curl -s http://127.0.0.1:9997/v3/paths/list | head -40
```

装完在遥控端打开控制台，视频面板底部会显示**能不能用 H.265**。
显示不可用的话画质不变但带宽要翻倍，原因是 WebView 版本太老
（需要 ≥ 136）或 SoC 没有 HEVC 硬解——WebRTC 的 H.265 没有软解兜底。

机身相机不用配，`mediamtx.yml` 里已经填好了确认过的地址
`rtsp://192.168.1.105:8554/test`。它在狗那侧的网段，走 eth0 拉流。
但**先探一遍再信它**：

```bash
python3 tools/rtsp_probe.py rtsp://192.168.1.105:8554/test
```

会报出编码、分辨率、有没有音轨，并直接给出 `media.json` 该怎么填。
`codec` 和 `kbps` 填错不会黑屏，只会让带宽仲裁算错账——现场表现是
「明明只看一路却卡」，很难联想到是配置写错了，所以值得花这一分钟。

这个工具自己发 RTSP 请求，不依赖 ffmpeg（板子上多半还没装）。
探不到就换 `.103` 和 `.106` 试试，路径 `/test` 像是出厂默认，也可能已经变了。

机身相机只有一路码流，所以它**不被选为主视图时会显示为不可看**，
计划里会写明「选为主视图才能观看」。这是有意为之，不是故障——
详见 [media-architecture.md](media-architecture.md) 第十节。

### 20. 确认感知主机 ROS 可达，开点云

点云**默认关闭**，因为感知主机的 ROS 能不能连通至今没有现场验证过。
没验证过的东西不该在开机时就去连一台生产设备，所以先手工验，验通了再开。

板子上不需要装 ROS——网关直接说 ROS 的线上协议，理由见
[pointcloud-architecture.md](pointcloud-architecture.md)。
所以这一步只是**探测**，不用装任何东西：

```bash
# master 活着吗
curl -s --max-time 3 http://192.168.1.105:11311/ && echo " <- master 有响应"

# 话题在不在、类型对不对
python3 - <<'PY'
import xmlrpc.client
m = xmlrpc.client.ServerProxy("http://192.168.1.105:11311")
code, msg, topics = m.getPublishedTopics("/probe", "")
for name, typ in sorted(topics):
    print(f"{name:45s} {typ}")
PY
```

要在输出里看到 `/lidar_points  sensor_msgs/PointCloud2`。

**看不到 master 响应**，说明 ROS 没起或地址不对，点云这条路走不通，
退路见 [hardware-integration.md 第一节](hardware-integration.md)。

通了就开起来。最省事的办法是在控制台的「设置」里勾上「启用点云回传」，
填好下面两项后保存，网关自己重启。

注意「本机在 ROS 网络中的地址」**必须填与狗直连那块网卡的地址**
（`192.168.1.120`），不能填 MESH 侧的 `192.168.10.2`——感知主机要反向连回来
取数据，填错的症状是注册成功但一条数据都收不到，很难查。这一条网关会当场拦下：
填一个不属于本机的地址会被直接拒绝。

也可以走命令行：

```bash
sudo bash deploy/install.sh \
    --robot-ip 192.168.1.103 \
    --perception-ip 192.168.1.105 \
    --bind 192.168.10.2 \
    --cloud --ros-host 192.168.1.120
journalctl -u x30-gateway -f
```

在遥控端控制台点「订阅点云」，日志里应当出现：

```
[cloud] 已启动点云订阅 /lidar_points
[ros] 已订阅 /lidar_points
```

面板右上角会显示实时点数和体素边长。**不看的时候记得停**——
订阅期间会一直占约 1.5 Mbps，不停的话视频会跟着变卡。

带宽不够时调「设置」里的「下行帧率」和「单帧点数上限」，各减半即
1 Hz / 10000 点。也可以直接改 `/opt/x30/conf/gateway.conf` 里的
`cloud_hz` 与 `cloud_points`，改完 `systemctl restart x30-gateway`。

### 21. 验证手柄物理控件可读

在手柄上用浏览器打开 `http://<板子IP>:8080/gamepad.html`，按任意键唤醒，
然后逐个拨动摇杆、按遍所有按键和拨轮。

**如果页面提示没检测到任何手柄**，说明摇杆没接到 Android 输入层
（这类地面站的摇杆常常直接走 S.BUS 到电台）。这种情况要找供应商要
「Android 手柄键值接口」文档，触摸屏虚拟摇杆则不受影响。

能读到的话按这个顺序走：

1. 点**「测量静止漂移」**（松开摇杆再点）。它会量出摇杆的静止偏移并给出
   死区建议。物理摇杆或多或少都有漂移，死区取小了狗会自己缓慢挪动，
   取大了近距离微调会很钝
2. 用**映射向导**逐项对应：点一行，再拨对应的控件。急停务必设一个
   独立物理键 —— 它在实现里不参与控制权判断，任何时候按下都立即生效
3. 点**「应用到控制台」**。诊断页和控制台同源，映射直接写进本机存储，
   回控制台刷新就生效，不用复制粘贴
4. 顺手把那段 JSON 也发回来一份，好让默认配置跟着改

**标准布局的手柄不用做这一步**。办公桌上拿普通 USB 手柄联调时，
浏览器报 `mapping: "standard"` 的话控制台会自动套用内置映射。
唯独急停不给默认值 —— 在不认识的手柄上猜急停键，按错比没有更糟。

控制台的摇杆面板下方有一条手柄状态栏，会显示当前用的是自定义映射、
标准布局、还是没有可用映射。**物理手柄一旦离开死区就自动接管**，
松开就交还给触摸摇杆，不需要手动切换。

状态栏上还有一个**死人开关**选项，默认关闭。打开后必须按住指定按键才能
推动，松手立即停。人员密集的场地建议打开；空旷场地长时间作业时多按一个键
会很累，可以关掉。要用的话记得先在诊断页里把「死人开关」那一行也映射上 ——
开了却没映射的话摇杆会直接锁死（状态栏会写明原因，这是有意的：
比"以为开着其实没开"安全）。

板子那侧通了之后，遥控端装 `android-app/` 里的应用，填板子 IP 和端口 8080。

## 排查

出问题先跑体检，它覆盖了下表大半的成因，而且会直接说下一步做什么：

```bash
bash deploy/checkup.sh
```

下表是体检没覆盖到、或需要人判断的部分。

| 症状 | 多半是什么 |
| --- | --- |
| 机器狗上电后板子不亮 | 没配上电自启，还在等人按 Power 键 |
| ping 得通 IP，域名解析不了 | 默认路由没走 4G，被 eth0 抢了 |
| 走远就断 | 天线没接，或装在金属外壳里没引出来 |
| 网关打印"未收到数据"，但指令发得出去 | `network.toml` 没登记本机，或 `ips`/`ports` 索引没对齐 |
| 手柄打开控制台白屏 | 绑错了 `--bind` 地址，或防火墙挡了 8080，或不在同一网段 |
| 控制台连上但遥测全是灰的 | 网关活着但收不到机器狗数据，回到第一行 |
| 摇杆推了没反应 | 没点「申请控制权」，或机器狗不在踏步/力控站立状态 |
| 原厂 App 一开，手柄和本系统都控不了 | 两个 0x21 源在抢运动主机。用原厂手柄时不要点「申请控制权」；用本系统时把原厂 App 关掉。网关没人 claim 时已不再发心跳 |
| 物理手柄推了没反应 | 状态栏显示"无可用映射"，去 `gamepad.html` 跑一遍向导 |
| 松开手柄狗还在慢慢走 | 死区太小压不住摇杆漂移，重测漂移并调大死区 |
| 手柄按键连发一串指令 | 不该出现；若出现说明上升沿判定被绕过，查 `gamepad.js` |
| 点上下楼没反应，步态不变 | 地形图模块没配好，查 `--perception-ip` 与 `.105` 可达性 |
| 视频面板是黑的 | `media.json` 的 `webrtc_base` 填成了 127.0.0.1，遥控端够不到 |
| 提示 H.265 不可用 | WebView < 136 或 SoC 无 HEVC 硬解，WebRTC 没有软解兜底 |
| 视频一开控制就卡 | 相机用了 VBR 把链路吃满，改成 CBR 并压低码率 |
| 机身相机显示"只有一路码流，选为主视图才能观看" | 不是故障，它确实没有子码流，点它当主视图即可 |
| 机身相机取不到流 | 用 `tools/rtsp_probe.py` 重探；`/test` 是文档外接口，换固件后可能变 |
| 点云面板一直"连接中" | `--ros-host` 填成了 MESH 侧地址，感知主机反连不回来 |
| 点云状态报"没有发布者" | master 通了但雷达驱动没起，在 `.105` 上查 |
| 一开点云视频就卡 | 两者抢 MESH 带宽，调低 `--cloud-hz` 或不看时退订 |
| 点云状态里 dropped 一直涨 | 链路发不动，降 `--cloud-points` |
| 走着走着突然停下 | MESH 掉包触发看门狗；查 `journalctl` 有没有租约超时 |
| 运行一段时间后卡顿 | 散热不够降频，看遥测盘的 CPU 温度 |
