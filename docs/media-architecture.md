# 视频与音视频对讲架构

覆盖优先级里的第 4、5 项：狗自带相机视频、双光布控球视频与云台、音视频对讲。

本文先记结论和依据，再讲实现。**几个关键选型是查证过的，不是拍脑袋，
依据都写在下面**——这些决定改起来代价很大，值得先说清楚。

## 一、为什么是 WebRTC

是**对讲**这个需求倒逼的，不是视频。

单看视频分发，RTSP、HLS、MJPEG 都能用，而且更简单。但对讲要求**双向、低延迟**，
上面三个全是单向的，上行语音没地方走。用 WebSocket 裹裸流虽然能双向，
但没有抖动缓冲和回声消除，对讲会变成一团糊。

WebRTC 一次性解决四件事：

- 天生双向，音频视频复用同一条 PeerConnection
- 自带抖动缓冲、丢包隐藏、**回声消除**。AEC 是对讲的刚需，
  没有它狗那侧的喇叭会把操作员的声音再采回去，形成啸叫
- 走 UDP，丢包不会像 TCP 那样触发重传队头阻塞把画面卡住
- 端到端延迟能压到 200 ms 以内

代价是比 RTSP 转发复杂。这个代价必须付，因为对讲没有更省事的替代方案。

## 二、编码格式：H.265 可以用，但必须能退回 H.264

原计划是「统一用 H.265，同画质码率约为 H.264 的一半」。在 20 Mbps 的 MESH
上这个便宜很值钱。但 WebRTC 对 H.265 的支持历史上一直很差，所以查证了一下：

**Chrome 136（2025 年 3 月）起，H.265 在 WebRTC 里默认开启**，桌面、Android、
Android WebView 三个平台同时生效。所以 H.265 这条路是通的。

但有两个限制，**都直接影响我们**：

1. **只有硬件解码，Chromium 没有内置 H.265 软解**（专利原因，不打算做）。
   设备 SoC 不支持 HEVC 硬解就完全用不了。好在 Android 侧硬件覆盖率约 86%，
   现代 SoC 基本都有。
2. **需要 WebView ≥ 136**。这是真正的风险点：**工业安卓地面站的系统常年不更新**，
   拿到手可能是 Android 9 配一个 2019 年的 WebView，那就没有 H.265。

所以不能假定 H.265 可用，**要在运行时协商**：

```
遥控端连上 → 用 MediaCapabilities API 探测本机能解什么
          → 通过既有 WebSocket 上报 media_caps
          → 网关据此决定发 H.265 直通路径还是 H.264 路径
```

探测代码在 `web/app.js` 里，一行 API 调用的事，但**必须真探测，不能看
UserAgent 猜**——同一个 Chrome 版本在不同 SoC 上结论可能不同。

## 三、能不转码就不转码

这是本文最重要的一条实现原则。

原先设想「所有码流都进 RK3588 用 MPP 重编码，统一出口」。但仔细想，
**IP 摄像机自己就能编出我们想要的码流**：几乎所有球机都支持主/子码流，
分辨率、帧率、码率、编码格式都能在球机自己的界面或 ONVIF 里配。

那就在球机上直接配好，RK3588 只做 **RTP 转封装（repackage）而不解码重编**：

| | 转码 | 直通 |
| --- | --- | --- |
| CPU 占用 | 高，每路都吃编解码器 | 几乎为零 |
| 延迟 | 多 50–150 ms | 只有转封装开销 |
| 画质 | 二次编码有损失 | 无损 |
| 复杂度 | 要接 MPP，要调参 | 只处理 RTP |

结论：**直通是默认路径，转码是兜底路径。**

MPP 硬编只在两种情况下才用：

1. 遥控端不支持 H.265，而球机只能出 H.265 → 必须转成 H.264
2. 想给只有单路码流的源造一张低码率缩略图 → 必须重编码

第 2 种情况目前只有机身相机会碰到，见第十节 —— 结论是暂不做。
原先担心的「机身相机给裸帧所以必须编码」没有发生，它直接出 RTSP。

配套的球机配置建议（在球机自己的界面上设）：

| 码流 | 分辨率 | 帧率 | 码率 | 编码 | 用途 |
| --- | --- | --- | --- | --- | --- |
| 主码流 | 1920×1080 | 25 | 3 Mbps CBR | H.265 | 当前观看的那一路 |
| 子码流 | 640×480 | 10 | 400 kbps CBR | H.264 | 缩略图，兼容性优先 |

**子码流刻意用 H.264**：它是缩略图，码率本来就低，H.265 省下的那点带宽
不值得冒兼容性风险；而且遥控端万一不支持 H.265，子码流还能直接看。

**用 CBR 不用 VBR。** VBR 在画面剧烈变化时（狗在走、云台在转，这是常态）
码率会飙上去，把 MESH 占满，然后控制报文排队、延迟起尖峰、租约超时、狗自己
停下。宁可画质恒定差一点。这条在 [system-architecture.md](system-architecture.md)
里作为「控制流必须优先于视频」讲过，这里是它的具体落实。

## 四、用 MediaMTX 做媒体路由，不自己写

WebRTC 的信令、ICE、DTLS、SRTP 加起来是个大工程，自己写不现实。查了三条路：

| 方案 | 评价 |
| --- | --- |
| Google libwebrtc | 功能最全，但体积巨大、交叉编译很痛，嵌入式场景公认难搞 |
| GStreamer webrtcbin | 灵活，能接 MPP，但要拖进 libnice/libsrtp/GStreamer 全家桶 |
| libdatachannel | 轻量，但 RTP 打包要自己做，且**没有拥塞控制** |
| **MediaMTX** | **选它** |

选 MediaMTX 的理由：

- **单个静态 Go 二进制，零运行时依赖**，官方提供 linux/arm64 构建。
  这和本项目「少一个依赖就少一处坑」的部署哲学完全一致，扔上板子就能跑
- 同时做 RTSP 客户端（从球机拉流）和 WebRTC 服务端（发给遥控端），中间不解码
- **支持 WebRTC publish（浏览器 → 服务器）**，这正是对讲上行需要的
- H.264 / H.265 / Opus / G.711 都支持
- 在 RK3588 上是被大量实际项目验证过的组合

它不做转码。需要转码时配 `ffmpeg-rockchip`（带 `h264_rkmpp` / `h265_rkmpp`）
单独起一路，把结果推回 MediaMTX。这正好呼应第三节：转码是兜底，不是主路径。

## 五、进程隔离：媒体崩了不能影响控制

**媒体服务与控制网关必须是两个进程。** 这不是洁癖，是安全要求。

`x30_gateway` 是零依赖单二进制，承载 50 Hz 轴指令、看门狗和急停，
**它绝对不能崩**。而媒体那套东西依赖多、状态复杂、要处理来自摄像机的不可信
输入，崩溃概率高得多。把它们塞进一个进程，等于让视频解析的野指针有机会
带走急停。

所以：

```
x30_gateway   零依赖，控制 + 遥测 + 媒体编排信令      ← 安全关键，不能崩
mediamtx      媒体路由，独立 systemd 服务             ← 崩了自动重启，控制不受影响
ffmpeg        仅在需要转码时起，由网关按需拉起         ← 崩了降级到缩略图
```

网关只**编排**媒体，不搬运媒体字节：它知道有哪些源、当前谁是主视图、
遥控端能解什么码，然后把一份「媒体计划」下发给遥控端，由遥控端自己去
MediaMTX 拉流。网关不碰视频数据本身。

## 六、媒体计划：带宽策略落到协议上

同一时刻只有一路能走全码率（依据见带宽预算）。这个约束必须由网关强制，
不能指望遥控端自觉——两个客户端各自选全码率就会把链路吃满。

网关维护一份源清单，为每个客户端算出一份「媒体计划」：

```json
{
  "t": "media_plan",
  "main": "ptz_vis",
  "sources": [
    { "id": "ptz_vis", "name": "布控球可见光", "available": true,
      "quality": "main",
      "path": "ptz_vis_main", "codec": "h265", "kbps": 3000 },
    { "id": "ptz_ir",  "name": "布控球热成像", "available": true,
      "quality": "thumb",
      "path": "ptz_ir_sub",  "codec": "h264", "kbps": 400 },
    { "id": "dog_cam", "name": "机身相机",     "available": false,
      "reason": "该源只有一路码流，选为主视图才能观看" }
  ],
  "budget_kbps": 3800,
  "total_kbps": 3400,
  "webrtc_base": "http://192.168.10.2:8889"
}
```

规则：

- **看视频不需要控制权。** 多人围观是正常需求，不该和操控权绑定
- 但**全码流全局只有一份**。已经有人在看全码率时，第二个客户端只能拿缩略图，
  并且会收到明确说明，而不是默默降级
- 遥控端切换主视图 → 网关重算计划 → 广播给所有受影响的客户端

## 七、对讲的音频通路

上行（操作员说话）：

```
手柄麦克风 → WebRTC publish → MediaMTX → RK3588 播放到喇叭
```

下行（现场声音）：

```
球机拾音器 → RTSP 内嵌音频 → MediaMTX → WebRTC → 手柄喇叭
```

两侧硬件要确认：

- **狗那侧**：优先用球机自带的拾音器和音频输出，省一套硬件。
  但要确认它的音频回传是走 RTSP 内嵌还是 ONVIF back-channel——
  **国产球机对 back-channel 的支持普遍不完整，这是本节最大的风险点**。
  兜底方案是在 RK3588 上插一个 USB 免驱声卡接喇叭麦克风，
  用 `ffmpeg` 从 MediaMTX 拉流写 ALSA。这个方案不依赖球机任何特性，
  建议**直接按兜底方案备料**，球机能用算白赚
- **手柄那侧**：安卓地面站自带麦克风喇叭。工地噪音大，
  做成**按住说话**而不是常开，既避免啸叫也省带宽

音频编码用 **Opus**，双向各 64 kbps 足够语音，浏览器原生支持，
WebRTC 里是默认协商项。

## 八、球机接入：GB28181 只用于云台与对讲，视频仍走 RTSP

现场确认球机同时支持 **GB28181 与 RTSP**，且带语音对讲。据此定下分工：

| 能力 | 走什么 | 理由 |
| --- | --- | --- |
| 视频 | **RTSP** | MediaMTX 原生支持；**它不支持 GB28181**（功能请求挂了两年未实现） |
| 云台 | **GB28181** | 已确认支持，不必再赌 ONVIF |
| 对讲 | **GB28181** | 同上 |

不为了统一而全走 GB28181：视频这条链路 RTSP 已经跑通且更简单，
而 GB28181 在这里唯一的优势（标准化互通）我们用不上——链路两端都是自己的设备。

### 对讲的时序是反的

GB28181 的语音对讲不是「平台推流给设备」，方向和视频点播**相反**：

```
平台 → 设备   MESSAGE（Broadcast XML）
设备 → 平台   200 OK
设备 → 平台   INVITE（带 SDP，指定它要在哪个端口收音频）   ← 设备主动
平台 → 设备   200 OK（带平台自己的 SDP）
设备 → 平台   ACK
平台 → 设备   RTP 音频流
```

**传输方式由设备端决定**，平台只能配合。三条查到的实际约束：

- 编码**必须 G.711A（PCMA）、8000 Hz、单声道**。海康大华都这样，设错了没声音
- 设备默认走 **UDP**。公网对讲要设备主动连平台，需新固件并打开「启用 TCP 广播」。
  **我们全在 `192.168.10.0/24` 局域网内，UDP 就够，这个坑正好绕开**
- 海康 SIP 配置里的「收到 ACK 后发流」默认关闭，不开的话设备会以为会话结束直接发 BYE

音频链路打算这么接，避免自己写音频处理：

```
遥控端浏览器 --WHIP(Opus)--> MediaMTX --RTSP(本地)--> ffmpeg --RTP(PCMA)--> 球机
```

`ffmpeg` 一条命令就完成 Opus 解码、重采样到 8k、PCMA 编码、RTP 打包，
我们只需要写 SIP 信令部分。

### 两个 GB28181 角色不要混

后面会影响架构，先记着：

| 角色 | 谁注册给谁 | 用途 |
| --- | --- | --- |
| RK3588 当**上级平台** | 球机注册到 RK3588 | 云台、对讲（现在要做的） |
| RK3588 当**下级设备/网关** | RK3588 注册到云平台 | 4G 上传（如果对方是国标平台） |

云平台是否为国标平台目前**未定**。如果是（公安、应急管理这类基本都是），
SIP 层就该按双角色可复用来写，而不是够用就扔。写的时候会把信令编解码
与角色逻辑分开，留出这个余地。

## 九、待现场确认

按影响大小排：

1. **遥控端 WebView 版本。** 决定能不能用 H.265。
   在手柄上打开 `chrome://version` 或访问诊断页看
2. **球机品牌型号与 GB28181 参数。** 上面那些坑都是厂商相关的，
   要拿到设备编号（20 位国标编码）、SIP 域、认证口令
3. **云平台是不是国标平台。** 决定 SIP 层要不要做成双角色
4. **机身相机的实际编码与码率。** 地址已确认（见下节），但 SDP 里报的
   编码和实际码率还没实测，用 `tools/rtsp_probe.py` 一条命令就能出结果

## 十、机身相机

取流方式已确认，走 RTSP：

```
rtsp://192.168.1.105:8554/test
```

这是三种可能里最省事的一种 —— 直接进 MediaMTX 转封装，既不用写 ROS 图像桥接，
也不用 MPP 编码。原先担心的「只有 ROS image topic，得多花几周」没有发生。

三个容易踩的点：

**它在狗那侧的网段。** `192.168.1.105` 是感知主机，挂在 eth0 上，
而 WebRTC 是从 eth1 发出去的。拉流走一张网卡、发流走另一张，
互不抢带宽，这其实是好事。但配防火墙时别把 eth0 的出站给堵了。

**它本质是一只 USB 摄像头，不是网络相机。** 厂家拓扑图显示这是一只
「广角相机 ×1」，通过 **USB 2.0 接在感知主机上**，`8554` 那路 RTSP 是
感知主机上的软件把它转出来的。两个后果：

- USB 2.0 的实际可用带宽约 300 Mbps，UVC 相机在这个档位通常出 MJPEG 或
  低分辨率 YUV。也就是说感知主机很可能在**软件转码**成 H.264 再发 RTSP，
  画质和延迟都不会太好，`rtsp_probe.py` 一探便知
- **它和地形图模块抢的是同一颗 CPU。** 感知主机同时负责上下楼要用的地形图，
  以及我们订阅的点云话题。长时间拉这路视频有没有影响到地形图的实时性，
  属于必须实测的事 —— 万一有，宁可不要这路视频，上下楼比它重要得多

所以它始终只是加分项，双光布控球才是主力视频源。

**它只有一路码流，没有子码流。** 这一点直接影响带宽仲裁：
本系统的缩略图机制依赖子码流，而机身相机拿不出低码率的那一路。

处理办法是**不给它配 `sub`，让它在非主视图时标为不可看**，
计划里会带上「该源只有一路码流，选为主视图才能观看」。
听起来像功能缺失，其实是这里唯一站得住的选择：另一条路是拿 2 Mbps 的
主码流去充当「缩略图」，那样光它一路就吃掉大半预算，
现场表现是「没看几路就卡」，而且极难联想到是缩略图的锅。

顺带说明一个实现细节：`MediaRegistry::Pick()` 允许主码流向下回退到子码流
（解不了 H.265 时退到 H.264），但**不允许子码流向上回退到主码流**。
这个不对称是有意的 —— 向上回退会让带宽预算在无声中失效。

真要给它一张缩略图，得在 `mediamtx.yml` 里用 `runOnDemand` 起一路
ffmpeg 转码。这是成本问题不是能力问题：转码要占 MPP 和 CPU，
而机身相机通常只在需要时切过去看一眼，为它常年养一路转码不划算。
等现场确认真有这个需求再加。

### 装机时先探一遍

`media.json` 里的 `codec` 和 `kbps` 填错**不会黑屏**，只会让带宽仲裁
算错账 —— 表现是「明明只看一路却卡」，很难联想到是配置写错了。
所以值得实测一次：

```bash
python3 tools/rtsp_probe.py rtsp://192.168.1.105:8554/test
```

它直接发 RTSP DESCRIBE 读 SDP，不依赖 ffmpeg（装机当天板子上多半还没装），
报出编码、分辨率、有没有音轨，并给出 `media.json` 该怎么填。

还要留意路径 `/test` 像是出厂默认，换固件或改配置后可能变。
取不到流时先用这个工具重探一遍，别一上来就怀疑网络。

## 十一、2.4G 链路下的画面：绕开网关，原生解 RTSP

前面十节讲的是 MESH 链路：网关下发媒体计划，客户端按计划从 MediaMTX 拉 WebRTC。
**2.4G 链路完全不是这套东西**，这一点如果记错，会往网关方向查很久而毫无进展。

2.4G 是**遥控器与狗直连**：

```
G20 手柄 --2.4G--> 接收机 --机身交换机--> 运动主机 192.168.1.103（控制）
                                    └--> 感知主机 192.168.1.105:8554（RTSP 画面）
```

网关开发板**不在这条链路上**，遥控器在 2.4G 下根本连不到它。所以：

- 拿不到 `media_plan`，媒体计划那一整套仲裁在这条链路上不存在
- 够不到 MediaMTX，WebRTC / WHEP 那条路整条不成立
- 改网关（监听面、ICE 候选、按客户端算 `webrtc_base`）对 2.4G 一点用都没有

狗自己只提供 RTSP，而 **WebView 放不了 RTSP** —— 这就是 2.4G 下控制正常、
画面却一直停在「等待拉流」的全部原因。它不是网络问题，也不是相机问题
（原厂 App 在 2.4G 下能出画面，正说明相机和链路都是好的）。

办法是在 App 里原生解码（`android-app/.../NativeVideo.java`，Media3 RTSP），
画面垫在 WebView 底下。三个不显然但必须这么做的点：

**socket 必须绑到 2.4G 那张网卡。** G20 射频起来后是虚口 `ar_net0`，系统
`ConnectivityManager` 往往看不见它，普通 socket 会被安卓按「默认网络」路由出去，
结果是 `Network unreachable` —— 和 `RadioLink` 里 UDP 踩过的是同一个坑。
所以给播放器塞一个自己的 `SocketFactory`，逐个 socket 做 `SO_BINDTODEVICE`。

**先走 RTP over TCP。** 默认是先试 UDP、收不到数据再退 TCP：既白等一个超时，
更麻烦的是那几个临时 UDP 端口还得各自绑对网卡（它们不经过我们塞进去的
`SocketFactory`）。走 TCP 时 RTSP 与 RTP 复用同一条连接，绑住这一条，整路流就
都在 2.4G 上。但也不死磕：个别 RTSP 服务不支持 TCP interleaved，所以失败后换
另一种再试，报错里会写清用的是哪一种。

**画面垫在 WebView 底下，而不是塞进网页。** `PlayerView` 排在 `WebView`
前面（也就是画在它下面），SurfaceView 会把自己那块矩形凿成透明；网页则在
`html.native-video-on` 下把这几层背景透出去。谁少做一半，结果都是「明明在放
却看不到」。矩形位置只有网页知道（横幅、布局都会挪它），由网页按
`devicePixelRatio` 换算成设备像素报给原生。

带宽上这条链路很窄，所以只放机身相机一路。布控球在网关那侧的
`192.168.10.0/24`，2.4G 到不了，界面上如实标成不可用而不是让它干等。
