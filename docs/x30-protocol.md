# X30 接口速查

从《绝影 X30 API Documentation (beta) V1.0.5-0, 2025-08-21》与
《绝影 X30 Pro 应用手册 V2.0.4-0》提炼。代码实现见
[`rk3588/include/x30/protocol.hpp`](../rk3588/include/x30/protocol.hpp)。

## 主机分布

| 主机 | 地址 | 用途 | 本机是否有 |
| --- | --- | --- | --- |
| 运动主机 | `192.168.1.103` | 运动控制，UDP 43893 | 有（已 ping 通） |
| 感知主机 | `192.168.1.105` | 地形图、传感器驱动、ROS 1、RTSP 8554 | 有 |
| 智能控制器 | `192.168.1.106` | 建图定位导航（`jy_cog`） | **厂家图上有，待验证** |

雷达自成一个网段，我们从尾部调试网口够不到，只能经感知主机的 ROS 话题拿：

| 地址 | 说明 |
| --- | --- |
| `192.168.2.105` | 感知主机网口0，接雷达交换机 |
| `192.168.2.106` | 智能控制器网口2，接雷达交换机 |
| `192.168.2.x` | 4× Livox Mid-360，挂在独立的雷达交换机上 |

早期资料称本机不含智能控制器，但厂家 2026-08 给的拓扑图上画着。
`.106` 若真在，`jy_cog` 的建图定位和 `CustomMsg` 消息定义都能直接用，
影响不小 —— 见 [system-architecture.md](system-architecture.md)。

## UDP 报文格式

小端。所有报文以 12 字节头开始：

```c
struct CommandHead {
  uint32_t code;             // 指令码
  uint32_t paramters_size;   // type=0 时是"指令值"，type=1 时是 data 长度
  uint32_t type;             // 0 = 简单指令, 1 = 复杂指令
};
```

复杂指令在头后面跟 `paramters_size` 字节的负载，发送长度是
`sizeof(head) + paramters_size`，不是整个结构体。

指令码高两位十六进制数字标识发送者：`0x21` = 遥控终端，`0x31` = 自主算法模块。
载荷计算机充当遥控终端，用 `0x21`。

## 指令（发往 `192.168.1.103:43893`）

| 功能 | 指令码 | 指令值 |
| --- | --- | --- |
| 心跳（≥2 Hz，必须） | `0x21040001` | — |
| 连接确认（心跳开始后发一次） | `0x21020001` | — |
| 卸力（急停后解除关节自锁；旧坐↔站） | `0x21010202` | — |
| RL 趴下（原厂手柄） | `0x21010222` | — |
| RL 起立（原厂手柄） | `0x21010223` | — |
| 进入力控站立 | `0x2101020A` | — |
| 起步 ↔ 停步 切换 | `0x21010201` | — |
| 手动模式 | `0x21010C02` | — |
| 非手动模式 | `0x21010C03` | — |
| 身高档位 | `0x21010406` | 0=匍匐, 2=正常 |
| 软急停 | `0x21010C0E` | — |
| 保存数据并退出 | `0x010C01`（jy_exe <2.2.45 用 `18`） | — |

`0x21010222` / `0x21010223` **不在公开 API 文档里**。对照运动主机
`deeprcs` 日志：原厂手柄起立打的是 `Received RL-StandUp … 0x21010223`，
趴下是 `Received RL Sit Cmd … 0x21010222`；文档那条 `0x21010202` 打的是
`Received stand up or sit down command`，轨迹又快又硬。网关的「坐 / 站」
跟原厂手柄走同一对码。

`0x21010202` 日常不起/趴，只作**卸力**。软急停 `0x21010C0E` 会趴下并锁关节，
之后再发 RL 起/趴会被主机吞掉。原厂 App「卸力」、手册急停后按 ⑤/㉑，
以及 2026-08-10 硬件急停松开后的第一条指令，都是 `0x21010202`
（日志 `Robot is waitting to stand up`）。卸力后再发 RL 起立。

RL 起立成功后，遥测的 `basic_state` **仍报 0（坐下）**。现场 10:45
起了一次，之后连点四次「坐」，运动主机收到的全是 `0x21010223`。
网关必须自己记住上次发的是起还是坐，不能信这份遥测。芯片上会显示
「RL 站立」，以免看起来像没起来。

步态，仅踏步态可切：

| 步态 | 指令码 | 最大前向 | 最大横向 | 最大偏航 |
| --- | --- | --- | --- | --- |
| Walk | `0x21010300` | 1.2 m/s | 0.8 m/s | 1.2 rad/s |
| 缓坡 | `0x21010402` | 0.7 | 0.3 | 0.7 |
| 越野 | `0x21010401` | 0.3 | 0.1 | 0.45 |
| 楼梯 | `0x21010405` | 0.3 | 0.1 | 0.45 |
| 楼梯(多帧) | `0x2101040A` | 0.6 | 0.1 | 0.45 |
| 45°楼梯(多帧) | `0x2101040B` | 0.3 | 0.1 | 0.45 |
| L-Walk | `0x21010420` | 1.0 | 0.5 | 1.0 |
| 山地 | `0x21010421` | 1.0 | 0.5 | 1.0 |
| 静音 | `0x21010422` | 1.0 | 0.5 | 1.0 |

匍匐档下 Walk 与缓坡的前向速度减半，且只支持这两种步态。
三种楼梯步态必须配合对应的地形图模式，否则不生效。
Run 步态没有独立的切换指令码，遥控器上是 D 键，协议文档未列出。

## 轴指令

四个码复用两套语义，取决于机器人当前的基础状态：

| 指令码 | 力控站立态 | 踏步态 |
| --- | --- | --- |
| `0x21010130` | 身高升降 | X 向线速度（前正后负） |
| `0x21010131` | 横滚 | Y 向线速度（**符号相反**） |
| `0x21010135` | 偏航 | 偏航角速度（**符号相反**） |
| `0x21010102` | 俯仰 | 无定义 |

- 取值 `[-32767, 32767]`，死区 `|v| < 655`
- **必须 50 Hz 持续发送**，超过 1 秒未收到即失效：
  踏步态下机器人减速到零，站立态下姿态回中
- **只在力控站立和踏步这两种状态下发。** 起立中 / 坐下中 / 坐下 / 初始站立
  里发轴（哪怕全是 0），力控身高通道会被读成「把身子按到最低」，
  原厂遥控器那种柔和起身/趴下就会变成猛起猛趴。网关在这些状态下停发轴。
- 换算：`v = axis / 32767 × 当前步态最大速度`
- Y 向与偏航的映射带一个负号。轴为正表示向右平移 / 向右转，
  而机体系 Y 轴左为正、偏航逆时针为正

## 遥测（运动主机单播回登记地址）

必须先在 `network.toml` 里登记本机 IP:Port，否则一条都收不到。

| 报文码 | 结构体 | 大小 | 频率 | 主要内容 |
| --- | --- | --- | --- | --- |
| `0x1008` | `RcsData` | 88 B | 200 Hz | 里程、运行时长、摇杆回显、10 位告警位域 |
| `0x1009` | `MotionStateData` | 60 B | 200 Hz | 基础状态、步态、腿式里程计位姿与速度 |
| `0x100A` | `ControllerSensorData` | 184 B | 200 Hz | IMU + 12 关节位置/速度/力矩 |
| `0x100B` | `ControllerSafeData` | 68 B | 1 Hz | 电机/驱动器温度、CPU 温度与主频 |
| `0x21050F0A` | `BatterySensorData` | 40 B | 0.5 Hz | 电压、电流、电量、4 路电池温度 |
| `0x11050F08` | 简单报文 | — | — | 身高档位，−1=匍匐 0=正常 |

结构体布局按 LP64 自然对齐，**不加 pack**。
代码里对每个结构体都做了 `static_assert(sizeof(...))`，改错字段编译期就会报。

### 基础状态

| 值 | 含义 |
| --- | --- |
| 0 | 坐下 |
| 1 | 起立中 |
| 2 | 初始站立 |
| 3 | 力控站立 |
| 4 | 踏步 |
| 5 | 坐下中 |
| 6 | 急停/跌倒 |

正常流程 `0 → 1 → 2 →(力控)→ 3 →(起步)→ 4`。
**发指令不会覆盖机器人自身的控制逻辑**：趴着的时候发起步会被直接忽略。
所以状态机要跟着遥测走，不能假设发了就生效。

### 告警位域（`RcsData.error_state`，从低位起）

IMU 超时 / 心跳超时 / 驱动器过温 / 驱动器故障 / 电机过温 /
电量低 / 电池过热 / GPIO 故障 / CPU 过温 / CPU 降频

### 急停来源（`RcsData.rcs_state_list.emergency_source`）

1 = 尾部软急停按钮，2 = 运动中自主触发，3 = 导航中自主触发，
4 = 自主充电中触发，5 = 客户端触发，6 = RAS 自主触发

## 感知主机 ROS 话题（`192.168.1.105`，ROS 1）

传感器：

| 话题 | 类型 | 频率 |
| --- | --- | --- |
| `/imu/data` | `sensor_msgs/Imu` | 200 Hz |
| `/livox/lidar` | `livox_ros_driver2/CustomMsg` | 10 Hz |
| `/lidar_points` | `sensor_msgs/PointCloud2` | 10 Hz |
| `/deeprobotics_local_height_map` | `sensor_msgs/PointCloud2` | — |

状态（与 UDP 遥测内容重叠，按方便取用）：
`/robot_basic_state`、`/robot_gait_state`、`/robot_velocity`、`/leg_odom`、
`/joint_states`、`/control_mode`、`/battery/level`、`/battery/voltage`、
`/motor_temperature`、`/driver_temperature`、`/mileage/*`、`/run_time/*`

速度链路：`/handle_state`（手柄）或 `/cmd_vel`（导航）
→ 经地形图模块修正 → `/cmd_vel_corrected` → 运动程序执行（非手动模式下）。
开发者可以直接发 `/cmd_vel_corrected` 来绕过地形图修正，但那样就失去了避障。

## 机身相机（`192.168.1.105:8554`，RTSP）

```
rtsp://192.168.1.105:8554/test
```

**这个接口不在官方文档里。** 68 页 API 文档中 camera / image / video / rtsp
出现次数为零，地址是现场确认出来的。因此不能指望它稳定：
换固件后地址或路径都可能变，厂商也没有兼容性承诺。
路径名 `/test` 尤其像出厂默认值。

只有一路码流，没有子码流 —— 这对带宽仲裁有影响，
见 [media-architecture.md](media-architecture.md) 第十节。

探测用 `python3 tools/rtsp_probe.py rtsp://192.168.1.105:8554/test`。

## 地形图模块（`192.168.1.105:43899` 或 ROS 话题）

| 功能 | UDP 指令码 | 话题 | 取值 |
| --- | --- | --- | --- |
| 原厂 LIO 开/关 | `0x0BAA0001`（UDP `:60000`） | — | 1=开 0=关，狗须站稳，回 0/-1 |
| 地形图模式 | `0x3101EE01` | `/height_map_mode` | 3=实心 4=格栅 5=无踢面 18=多帧准备 20=多帧 |
| 速度输入源 | `0x3101EE03` | `/vel_source` | 1=手柄 2=导航 |
| 避障策略 | `0x3101EE02` | `/brake_mode` | 1=减速 2=绕行 |
| 障碍高度阈值 | `0x3100EE04` | `/step_z_max` | 1=8cm 2=28cm |

推荐阈值：Walk/缓坡 8cm，越野/楼梯 28cm。
多帧模式只能在机器人静止时切换。

## 未开放的能力

- **关节级力矩直控**。Lite3 的 `Lite3_MotionSDK` 提供 MPC 级接口，
  X30 没有，API 只到指令/速度级。
- **视频**。API 文档中无任何摄像头相关接口。
