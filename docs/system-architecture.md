# 系统架构

目标形态：RK3588 装在机器狗背上，通过网线直连机身；遥控手柄经 MESH 自组网
接入同一个局域网；狗、RK3588、手柄三者互通。手柄上操控行走与姿态、上下楼，
并查看视频、双光布控球画面与气体监测数据。4G 用于把信息上传云端（后续做）。

## 为什么要加交换机

T6-Plus 只有两个网口，但要接的 IP 设备有四类：机器狗机身、MESH 电台、
双光布控球、气体监测。

eth0 独占给机器狗——这条链路承载 50 Hz 轴指令，不该和视频流混跑。
剩下三个设备只能共用 eth1，所以 **eth1 后面必须挂一个交换机**，
不能只接 MESH。

```
eth0 ── 机器狗机身          192.168.1.0/24
eth1 ── 工业交换机 ─┬─ MESH 电台      192.168.10.0/24
                    ├─ 双光布控球
                    └─ 气体监测
```

选 5 口千兆工业交换机，12V 供电，与板子共用同一路 DC-DC。布控球的码流
进来和转码后出去都走 eth1，但 eth1 是 2.5G，几 Mbps 的量完全不构成压力。

载荷网段用 `192.168.10.0/24`，**不要用 `192.168.2.x`** —— 机器狗自己的
第二个网口就是那个段，将来接进来会撞。

### 关于 .106：之前的判断可能是错的

我们此前依据的资料说本机不含智能控制器，因此 `.106` 不存在、官方 `jy_cog`
建图定位不可用、SLAM 必须自建。**厂家 2026-08 给的拓扑图上明确画着智能控制器**，
所以这个判断需要重新验证。

差别很大，值得优先确认：`.106` 若真的在，官方建图定位套件可用，
`livox_ros_driver2` 的 `CustomMsg` 消息定义也能从 `~/jy_cog/transfer/setup.bash`
直接拿到，而不用手工照着 API 文档敲结构体。整个自建 SLAM 的工作量可能省掉。

一条 ping 就能了结，`deploy/checkup.sh` 里已经带上了。

### 雷达在 192.168.2.0/24，不在控制网段

四个 Livox 挂在**独立的雷达交换机**上，自成一个网段。感知主机和智能控制器
各有一只脚跨在两边（`.2.105` / `.2.106`），负责把雷达数据取上来。

这条对我们有两个后果：

- 载荷网段坚决不能用 `192.168.2.x`，会和机身内部撞。我们用 `192.168.10.0/24`
- 板子从尾部调试网口接入，**够不到雷达交换机**。所以拿点云只能走感知主机的
  ROS 话题（现在就是这么做的），不能直连雷达。想直连的话得额外走一根线到
  雷达交换机，目前没有这个必要

### 尾部调试网口经过一个路由器 —— 这是遥测能否回来的关键

拓扑图上，尾部调试网口**不是直接挂在交换机上的，中间隔着一个路由器**。
这一点必须现场确认清楚，因为它决定整个遥测链路成不成立。

原因在于运动主机的遥测是**单播**的：它只往 `network.toml` 里登记过的那个 IP
发。这套机制要求板子和运动主机在**同一个二层网段**里，板子得真的持有
`192.168.1.120` 这个地址。

如果那个路由器是**桥接/交换模式**，尾部网口和交换机同属 `192.168.1.0/24`，
一切照原计划走。如果它是**路由 + NAT 模式**，板子会拿到另一个网段的地址
（比如 `192.168.8.x`），那么：

- 板子发得出指令（出方向经 NAT 没问题）
- 运动主机往 `192.168.1.120` 回发的遥测**永远到不了板子**
- 现象和"`network.toml` 没登记"一模一样，会让人在错误的方向上排查很久

判断方法很简单，插上网线先用 DHCP：

```bash
ip -br addr show eth0     # 拿到的是 192.168.1.x 还是别的网段？
ping -c3 192.168.1.103
```

拿到 `192.168.1.x` 且能 ping 通 → 桥接，按原计划配静态 `.120`。
拿到别的网段 → 路由模式，得换接入点：找交换机上的空口直连，
或者把路由器改成桥接（若可配）。**在这一点确认之前不要动 `network.toml`**，
否则会同时引入两个变量。

## 两条 UDP 通道，缺一不可

这是本项目最容易出错的地方。运动控制和地形图在**两台不同的主机**上：

| 通道 | 目标 | 用途 | 特性 |
| --- | --- | --- | --- |
| MotionClient | `.103:43893` | 心跳、轴指令、状态遥测 | 双向，需心跳 |
| TerrainClient | `.105:43899` | 地形图模式、障碍高度阈值 | **只写，无确认** |

楼梯步态必须两条通道配合。只发步态指令的话，运动主机会**静默忽略**：
不报错、不回任何东西，界面上按钮亮了但狗不上楼。

因为地形图通道收不到确认，`GaitCoordinator` 拿运动主机的步态遥测当确认用 ——
地形图没配好时步态切不过去，正好可以检测出来并给出可操作的错误信息。
详见 [app-protocol.md 的步态切换一节](app-protocol.md)。

## 带宽预算：20 Mbps 是硬约束

MESH 标称 20 Mbps。这是近距离空口速率，远距离、非视距、狗在移动时会明显下降，
而且 mesh 的空口是共享的，实际可用按 **10–12 Mbps** 规划，不要按 20 排。

要跑的东西：

| 流 | 预算 | 说明 |
| --- | --- | --- |
| 控制 + 遥测 | ~50 kbps | 量很小，但**绝不能被挤掉**，见下 |
| 主视频（当前观看的那一路） | 3 Mbps | 1080p25 H.265 |
| 次视频缩略图 × 2 | 0.4 Mbps × 2 | 480p10，仅用于「看一眼有没有情况」 |
| 音视频对讲（双向） | 128 kbps | Opus 双向各 64 kbps，量小但**要低延迟** |
| 气体监测 | 可忽略 | 数值型，1 Hz 足够 |
| 点云 | 按需 2–3 Mbps | 体素降采样，1–2 Hz，**不常开** |
| 预留余量 | ≥ 3 Mbps | 链路劣化时的缓冲 |

三条由此得出的设计决定：

**视频统一由 RK3588 做出口，不透传 RTSP。** 布控球的原始码流先进 RK3588，
用 MPP 硬件编码器重新编码后再出去。透传的话三路加起来轻松超 20 Mbps，
而且码率不可控。

**用 H.265 而不是 H.264。** 同画质下码率约为一半，RK3588 支持 8K30 H.265 硬编，
这个便宜不占白不占。

**同一时刻只有一路走全码率。** 操作员正在看的那路给 3 Mbps，其余降到
480p10 的缩略图。切换观看目标时再切码率。三路都给全码率是放不下的。

### 控制流必须优先于视频

这是个真实的失效模式，值得单独说：视频一旦把链路占满，控制报文会排在视频
后面，往返延迟出现尖峰。而遥控端要 2 Hz 发心跳、网关 3 秒租约到期就撤销控制权
——链路一堵，机器狗就会自己停下，操作员会觉得「莫名其妙断控」。

两条措施：

- **给视频设硬上限，别让码率自适应一路涨到把链路吃满。** 总视频码率封顶在
  可用带宽的 60–70%，宁可画质差一点。
- 在 eth1 上做 QoS，控制端口的报文打高优先级（DSCP EF）并优先出队。

### 音视频对讲：技术选型被它倒逼

对讲的码率可以忽略（双向 Opus 加起来 128 kbps），但它对**架构**的影响很大，
因为对讲要求的是**双向、低延迟**，而视频分发只要求单向。

这直接排除了几个原本可选的方案：RTSP 拉流、HLS、MJPEG 都是单向的，
上行语音没地方走；WebSocket 裹裸流虽然能双向，但没有抖动缓冲和回声消除，
对讲会变成一团糊。

**结论是视频与对讲统一走 WebRTC。** 理由：

- 天生双向，音频和视频复用同一条 PeerConnection
- 自带抖动缓冲、丢包隐藏、**回声消除**——对讲里 AEC 是刚需，
  不然狗那侧的喇叭会把操作员的声音再采回去形成啸叫
- 走 UDP，丢包不会像 TCP 那样触发重传队头阻塞导致画面卡住
- 端到端延迟能压到 200 ms 以内，对讲和遥控观察都够用

代价是 RK3588 侧要跑一个 WebRTC 栈，比 RTSP 转发复杂不少。

两侧的音频硬件要先确认：

- **狗那侧**：多数双光布控球自带拾音器与音频输出（Audio In/Out 或内置喇叭），
  优先用球机自带的，省一套硬件。要确认它的音频是走 RTSP 内嵌还是 ONVIF
  back-channel，**后者不少国产球机支持得不完整，这是主要风险点**。
  实在不行就在 RK3588 上接一个 USB 免驱声卡加喇叭麦克风。
- **手柄那侧**：安卓地面站自带麦克风与喇叭，但工地环境嘈杂，
  建议做成**按住说话**而不是常开，既避免啸叫也省带宽。

### 点云要按需开

点云是这里面最贵的。四台 Mid-360 合并后原始点率很高，直接下发根本不可能。
规划是体素降采样后 1–2 Hz 下发，且**默认不开**，操作员需要时才拉。
建图本身在 RK3588 上跑，平常只把位姿（几十字节）发下去。

## 4G 只做运维，不做遥控

| 接口 | 用途 | 原因 |
| --- | --- | --- |
| MESH | 遥控链路 | 局域网直连，延迟低且稳定 |
| 4G | 远程运维、云端上传 | 运营商 NAT 后手柄直连不到；延迟抖动上百毫秒 |

遥控端要以 2 Hz 发心跳、网关 3 秒租约到期就撤销控制权，4G 链路一抖
机器狗就会自己停下。

**遥控端口必须挡在 4G 之外。** 协议目前没有身份认证，凡能连上 8080 的
客户端都能申请控制权驱动机器狗。用 `--bind` 绑到 MESH 那侧网卡的地址，
再加防火墙。做法见 [rk3588-setup.md 第 18 节](rk3588-setup.md)。

## 遥控手柄

安卓手持地面站，横持，屏幕居中，两侧各一个摇杆。从实物照片辨认出的控件：

| 位置 | 控件 |
| --- | --- |
| 左侧 | 左摇杆、L1、L2、一个二/三档拨动开关、一个圆形功能键 |
| 右侧 | 右摇杆、R1、R2、一个二/三档拨动开关、电源键、`^` 键 |
| 右下 | **红色圆形禁止标志按键**，形态上就是急停 |
| 顶边 / 侧边 | 两个滚轮或摇杆式拨钮（这类地面站上通常给云台俯仰与变倍用） |
| 右侧边缘 | 6 个 LED 指示灯（信号或电量） |
| 外部 | 两根外置天线 |

### 摇杆能不能读到，是个待验证的风险

**不少手持地面站的摇杆是直接走 S.BUS 接到电台的，根本不经过 Android。**
这类设备上 Android 侧只拿得到图传画面和遥测，读不到摇杆量。真是这样的话，
我们的 App 无论用 Gamepad API 还是原生 KeyEvent 都读不到，必须找厂家要
「Android 手柄键值接口」或 HID/AIDL 文档。

现场验证方法：在手柄上打开 `http://<RK3588_IP>:8080/gamepad.html`，
按任意键唤醒，然后逐个拨动摇杆、按遍所有按键和拨轮。这个诊断页会显示
浏览器能看到的全部轴与按键、各轴的行程范围、静止漂移，并能生成按键映射。

页面同时会测**静止漂移**并给出建议死区。摇杆有零点漂移是常态，
死区取小了会出现「松手后狗还在慢慢走」，这个量必须实测而不是拍脑袋。

### 摇杆通道：一套约定，杜绝符号错

输入有两种（触摸摇杆、物理手柄），输出也有两种（踏步态发速度、力控站立态
发姿态）。两两组合就是四套符号约定，各自为政的话必然出错 —— 而且是那种
最难查的错：**只在某一种状态下方向反了**。

事实上这个坑已经踩过一次。修复前，同一个「左摇杆右推」在踏步态下得到
原始轴 −1、在力控站立态下得到 +1，两种模式方向相反；右摇杆同理。
注意这个结论不依赖于「正方向到底是左还是右」—— 同一个物理动作在两种
模式下产生相反的轴值，无论如何都有一个是错的。

现在所有输入源都先归一到四个通道，**一律推杆方向为正**：

| 通道 | 物理控件 | 正方向 |
| --- | --- | --- |
| `fwd` | 左摇杆上下 | 前进 |
| `lat` | 左摇杆左右 | 左移 |
| `turn` | 右摇杆左右 | 左转 |
| `tilt` | 右摇杆上下 | 向上 |

输入侧负责转进来，输出侧负责转出去，中间只有这一套约定。
再加输入源（比如厂家 SDK 的摇杆）只要产出这四个值，不必再关心下游。

两侧的换算在 `tools/gamepad_test.js` 里各自镜像了一份，
并断言两种输出模式对同一通道值必须给出相同的原始轴。改了一边没改另一边，
测试就会红。这条断言是专门为上面那个 bug 立的。

### 急停走独立通路

那个红色禁止键应当映射为急停，并且在实现里**不参与控制权判断**——
协议里 `estop` 本来就是免鉴权的，任何客户端任何时候都能发。
如果这个键在硬件上是直接断电或断链的，那更好，软急停作为第二道。

### 死人开关：做成可选，默认关

「按住某个键才能推动，松手立即停」。控制权租约加看门狗已经能兜住掉线和
切后台，但兜不住**操作员还连着、手却离开了摇杆**这一类情况。人员密集的
场地里这条值得开。

做成可选是因为它改变操作习惯：多按一个键在长时间作业时很累，而空旷场地
未必需要。开关在控制台的手柄状态栏上，选择会记在本机，
和映射分开存 —— 它是操作策略，不该被重跑一遍映射向导冲掉。

两个实现上的取舍：

- **只闸摇杆，不闸按键。** 急停必须任何时候都发得出去；坐站、起步这些
  是有意识的单次按键，本来就不属于"松手就该停"的范畴
- **开了但没映射对应键时，摇杆一律锁死**，并在状态栏写明原因和解决办法。
  另一条路是"以为开着其实没开"，那比锁死危险得多

### 原厂手柄仍在网内：多了一个我们管不到的指令源

厂家拓扑图上有一个 **2.4G 接收机接在机身交换机上，配一只原厂手柄**。
也就是说除了我们这条链路，还有第二个能直接指挥运动主机的东西，
而它**完全在我们的控制权仲裁之外** —— 网关那套租约只管得住连到网关的客户端。

两个人同时推杆会怎样，取决于运动主机自己怎么裁决，公开资料没写。
最可能是「后到的指令覆盖先到的」，也就是两边会互相打架。**这必须实测**，
而且要在把狗架起来的状态下测：两边同时推杆，看它听谁的。

结论已经实测出来：网关只要一直发心跳和全零轴，原厂 App 一开，
两边就都控不了——运动主机把两个 0x21 源当成同一路 GamePad，
后到的全零轴把手柄的量盖掉，手柄的心跳又把网关的租约搞乱。

所以网关**只有控制台点了「申请控制权」才向运动主机发心跳和轴**。
没人 claim 时保持沉默，原厂 2.4G 手柄可以单独用。用本系统时把
原厂 App 关掉或放手，不要两头同时当指令源。

现场纪律：**同一时刻只有一个指令源**。原厂手柄当后备时，不要在
控制台点「申请控制权」；要用控制台时，原厂 App 不要开着抢杆。

不要关机是有理由的 —— 原厂手柄反而是目前最可靠的**后备控制**。
它走 2.4G 专用链路，不经过我们的 MESH、不经过网关、不依赖我们写的任何代码。
我们这边真出问题时，它是能把狗停下来的独立通路。所以第一次实机联调时
应当有人拿着它待命，这比我们自己的软急停更值得信任。

### 一个跨模块的约束：板子上不装 ROS

板子跑 Ubuntu 22.04，而 ROS1 Noetic 官方只支持 20.04。与其为了订阅两三个话题
背上整个 ROS 运行时（源码编译、conda、或 Docker，没一个干净），
不如直接说 ROS 的线上协议——XML-RPC 做发现，TCPROS 收消息。

代价是消息类型的 md5sum 要手工对齐，收益是板子上除了我们自己的二进制什么都不用装。
这和自己写 WebSocket、自己写 UDP 协议是同一个取舍。后面接 `/imu/data`、
`/leg_odom` 走的也是这条路。

## 待实机验证的推断

以下几点是从文档推断的，没有实机验证过，现场要重点确认：

- **多帧模式的两步切换**。文档把 18 和 20 分别标为"多帧准备"与"多帧"，
  代码按先发 18、隔 300ms 再发 20 实现。如果实机上一步到位，
  这里的中间步骤是多余的（但无害）。
- **退出楼梯后地形图模式的处理**。文档没有给"关闭地形图"的取值，
  代码目前只回设障碍高度阈值，不改地形图模式。
- **地形图指令的 0x31 前缀**。载荷计算机在运动通道上用 0x21（遥控终端身份），
  但文档给的地形图指令码是 0x31 前缀，代码照抄。如果实机拒收，
  试试改成 0x21 前缀。
